drupal-claude-skills

A shared Claude Code and Codex toolkit for Drupal open source contribution.

Overview

This package installs shared skills and client-specific agents into a Drupal workspace so either assistant can pick up a Drupal.org or GitLab work-item URL and carry it through the full contribution lifecycle: review, implementation, testing, and issue-record keeping, with explicit scoped approvals for code, dependency, and contribution changes.

The package itself is not a Drupal project. There's no PHP, no Composer, no web server here. Its output is the set of files installed into your Drupal workspace via: 

npx github:abhisekmazumdar/drupal-contrib-claude-skills

See the GitHub repository for source and issues.

Installation

Requirements

  • Node.js 18 or later (for npx)
  • Claude Code, Codex CLI/IDE, or both, installed and authenticated
  • Python 3 and PHP on the host for the command guard and MCP server
  • A running DDEV Drupal project
  • drupalorg-cli on PATH
  • GitLab CLI (glab), authenticated against git.drupalcode.org

Run it

npx github:abhisekmazumdar/drupal-contrib-claude-skills

Add a shell alias so you don't have to remember it:

# add to ~/.zshrc or ~/.bashrc
alias drupal-claude-skills='npx --yes github:abhisekmazumdar/drupal-contrib-claude-skills'

--yes skips npx's "ok to install?" confirmation. Safe here since this is a project you control.

Alternative: clone locally

Prefer a pinned copy (offline reuse, a specific commit, or editing the skills yourself)?

git clone git@github.com:abhisekmazumdar/drupal-contrib-claude-skills.git /path/to/drupal-claude-skills
npx /path/to/drupal-claude-skills

What the setup script asks

Where is your Drupal project? [drupal (auto-detected)]:

DDEV project name [my-drupal-project]:
Site URL [https://my-drupal-project.ddev.site]:
PHP version [8.4]:
MariaDB version [11.8]:
  • The Drupal project location is asked first so the DDEV project name can be auto-detected from .ddev/config.yaml.
  • If Drupal is at the workspace root, the location question is skipped entirely.
  • Press Enter to accept any default, or type a custom value.
  • Answers are saved to .drupal-contrib/install.json. Re-runs reuse recorded answers; --yes accepts defaults for new sites.

What happens

  1. .claude/skills/ is created (or updated) with all package skills
  2. .claude/agents/ is created (or updated) with all agents; external skills such as playwright-cli and drupalorg-cli (see External skills for the full list) are pulled from their upstream repos via npx skills if not already installed
  3. Client configuration is prepared: Claude permissions/hooks in .claude/settings.json and MCP in .mcp.json; Codex configuration in .codex/
  4. CLAUDE.md and/or AGENTS.md point to shared project details in .drupal-contrib/context.md
  5. .drupal-contrib/install.json is written with your answers for future re-runs

Re-runs always bring skills/, agents/ (in every rendered form — .claude/agents/, .codex/agents/*.toml, .drupal-contrib/agents/), and the Git-guardrail hook scripts fully in line with this version of the package — a local edit to any of these is overwritten, and a skill/agent removed upstream is deleted from the project too. These are pure toolkit output; nothing there is meant to be hand-tuned per project. Symlinks at these destinations are never followed or written through. CLAUDE.md/AGENTS.md get a managed block (delimited by <!-- drupal-contrib-claude-skills:begin/end --> comments) that's fully refreshed on every run; a project's own pre-existing content in the rest of the file is untouched, and the block is appended if the file existed before the toolkit's first install. Everything else (.claude/settings.json, .mcp.json, Codex's config.toml/hooks.json/rules) still uses the original preservation logic — package updates apply automatically, but a hand-edited config is left alone and a proposed replacement appears under .drupal-contrib/proposals/ for manual integration instead.

Updating

Installed via npx github:...: just re-run the same command. npx fetches the current main branch each time.

npx github:abhisekmazumdar/drupal-contrib-claude-skills

After installation

Open the workspace in either client and paste a Drupal.org issue URL (or use /drupal-issue-start in Claude Code and $drupal-issue-start in Codex):

https://www.drupal.org/project/ai/issues/3499692

Or run the entry-point skill directly:

/drupal-issue-start https://www.drupal.org/project/ai/issues/3499692

GitLab work-item URLs are also supported:

https://git.drupalcode.org/project/ai/-/work_items/3499692

The skill loads any prior work from issues/<nid>/README.md, fetches live issue state (every open MR, all inline and top-level comments), cross-checks other local issue records for backlinks to this one, then automatically checks out the most relevant MR locally and gives it a light preliminary read. The checkout itself needs no approval, since it's local and reversible. If more than one MR is open, it picks the most active one and lists the rest so you can redirect.

The resulting report leads with a verdict (RTBC-ready, close with a named gap, needs work with a named gap, or needs discussion), plus anything you need to know before trusting it: missing fork access, no push access, DDEV not running. Only then does it ask what you want to do.

Beyond the automatic recon checkout, agents pause at every approval gate. The skill relays each pause report back to you, and nothing is written, edited, composer require'd, committed, or posted without your explicit go-ahead.

Shared content and safe migration

.drupal-contrib/context.md contains the site table and runtime conventions. Skills resolve <skills-root> from the active client and pass it with the selected site. Complete agent procedures also live under .drupal-contrib/agents/; sequential phases remain together. Codex uses native tools and role definitions rather than Claude frontmatter tool names. If nested delegation is unavailable, the main conversation runs the requested role as a sibling agent and resumes its caller. If subagents cannot run, independent verification is reported unavailable.

.drupal-contrib/install.json stores a versioned configuration and hashes of installed files. The legacy .claude/claude-skills.lock.json is retained and its answers are imported. Skills, agents, and hook scripts are force-managed — always overwritten to match this version of the package, with anything removed upstream pruned from the project on the next run — since none of that is meant to be edited per project. CLAUDE.md/AGENTS.md instead upsert a single marked block on every run, leaving a project's own surrounding content alone. Everything else (client settings/config/hooks.json/rules) keeps the original preservation logic: existing custom settings, edited package files, and symlinks there are never overwritten. Proposals go under .drupal-contrib/proposals/, outside either client's discovery paths. Review and merge them before starting issue work. Re-run setup after accepting an exact proposal to record ownership. A manually merged file continues to be preserved on future updates.

External skills are downloaded into temporary staging directories, grouped by upstream repository for each client, then copied through the same preservation checks. Their source lock entries are retained for npx skills update; merge a proposed skills-lock.json first if needed. Upstream explicit-only skills receive missing Codex invocation-policy metadata. Existing metadata is preserved and conflicts are reported. Re-run setup after upstream updates; unsupported upstream tools remain a reported capability gap.

Activation and permission differences

Approve Claude's project MCP server interactively and inspect it with /mcp. In Codex, trust the workspace configuration and inspect/review/trust the hook through /hooks. Hooks awaiting trust are skipped. The installer never changes global trust or configuration.

The shared shell wrapper calls check-command.py, which requires Python 3. It recognizes destructive Git operations including git -C, combined flags, compound commands, and explicit shell wrappers. Bare force-pushes and the toolkit's reserved GitLab writes are blocked; --force-with-lease remains available with approval. Command arguments are not echoed into error messages.

Codex rules govern commands requesting execution outside the sandbox. Its current PreToolUse hook can deny a call but cannot force an approval prompt. Workflow approvals therefore remain instructions, supplemented by native permissions and rules. Hooks do not inspect arbitrary script contents, aliases, dynamic shell expansion, or later interactive stdin. They are a practical guardrail, not a complete enforcement boundary.

Keep Nora's implementation separate from Milo's report-only testing. Both may need to write local artifacts or exercise DDEV; a report-only role does not imply a completely read-only operating-system sandbox. Both clients share issues/; serialize record updates and use separate worktrees for concurrent code work. AI declarations name whichever assistants actually contributed.

Compatibility and validation

Target local macOS/Linux or WSL sessions with DDEV access. Native Windows and hosted cloud DDEV access are not validated. Codex must support repository skills, standalone custom agents, and trusted PreToolUse hooks. Local rule/configuration checks used Codex CLI 0.153.4; Claude Code 2.1.236 was available during development. No live Drupal issue lifecycle has been claimed as tested.

Automated tests cover all targets, repeated installs, legacy and multi-site configuration, user-edited files, symlinks, offline and grouped external installs, JSON/TOML generation, and command-guard decisions. Browser screenshots require the requested connected session: a new Playwright browser does not inherit the user's open tab or login.

Before a release, exercise an issue in each client: load context, recon, review, relay an approval, delegate tests, save screenshots, and resume the record in the other client. Confirm hook trust and MCP connectivity on the actual host.

Runtime references: Codex skills, custom agents, hooks, rules, and Claude project MCP configuration.

Agents

Four agents live in agents/, each with a persona name as a body-level identity. The persona name is cosmetic. The frontmatter name: field (matching the filename) is what every invocation and cross-reference actually uses.

Agent (name:)PersonaRole
drupal-issue-agent Nora Full review/implement/fix loop. The only agent that edits module code. Always invoked by drupal-issue-start, never invoked from a bare user phrase.
drupal-e2e-tester Milo Dedicated test phase. PHPUnit via DDEV plus Playwright browser e2e. Report-only. It never edits code, so the implementing agent is never the one verifying its own work.
drupal-repo-setup Wren Git/repo plumbing: locates, clones, installs missing Composer dependencies (with approval), checks out or worktrees a branch. recon mode (clone + checkout + fork-remote) runs unpaused since it's local and reversible; Composer install always pauses. After checkout, cross-checks the MR's actual GitLab target branch against the issue's declared version (a structured field for non-migrated issues, the last version-change comment for migrated ones) and flags a mismatch as a non-blocking setup issue.
drupal-issue-catchup Sage Re-briefs on an issue after time away. Diffs new activity against the local record, re-derives the verdict/next-action/blocker, and waits for direction. Never edits code.

Handoff flow

/drupal-issue-start → drupal-issue-agent (Nora) → drupal-repo-setup (Wren)
/drupal-issue-start → drupal-issue-agent (Nora) → drupal-e2e-tester (Milo)
/drupal-issue-start (Phase 5 routing) → drupal-issue-catchup (Sage)

Sub-agents can't talk to the user mid-run, so approval gates use a pause-relay protocol: an agent ends its run with a [PAUSE — awaiting user decision] report, drupal-issue-start relays it verbatim, and the agent resumes with the user's reply.

<site> (and its resolved <webroot>/<drupal-path>) flows through this whole chain alongside <nid>/<project>. It resolves once in drupal-issue-start Phase 0.5 and never re-resolves for any agent it hands off to.

Multi-site support

A workspace can hold more than one Drupal install (e.g. drupal/, cms/, an umami demo). bin/setup.js detects every top-level Drupal root, configures each as a named site, and marks one default. This is rendered into .drupal-contrib/context.md's ## Local environments table. The lockfile stores { sites: {...}, defaultSite }; older single-site lockfiles migrate automatically on the next run.

Site selection happens exactly once, in drupal-issue-start Phase 0.5, which matches the user's wording against the table's Name column (falling back to Default when unmentioned) and resolves <site>/<webroot>/<drupal-path>/DDEV project/site URL as concrete values. Those values then flow downstream unchanged through drupal-repo-setup, drupal-issue-agent, drupal-e2e-tester, and drupal-issue-catchup. None of them re-resolve or re-prompt for a site.

DDEV has no -C/--project flag, so any ddev command must run with cwd inside that site's root first.

Issue record format

Every issue gets a persistent record at issues/<nid>/README.md, written/updated by drupal-issue-start and appended to by issue-record-update.

  • ## At a Glance and ## Current State are snapshots, overwritten in place every session, never append-only.
  • ## Work Log and ## Related Issues are append-only.
  • Next action / Blocked on are sourced only from the current session, never accumulated across sessions.
  • The header's **Status:** field uses a fixed vocabulary so it's scannable across issues.
  • **Site:** appears in the header only once the workspace has 2+ configured sites.

Work Log archiving

issue-record-update keeps the README's ## Work Log capped at the 3 most recent sessions, moving anything older to issues/<nid>/history.md (newest-archived first). Neither drupal-issue-start nor drupal-issue-catchup reads history.md by default, only when a session genuinely needs pre-archive context.

issue-record-update runs automatically at the end of any session that did something: code reviewed, changed, tested, or a comment/push attempted. A pure read-only catchup skips it.

Drupal.org AI contribution policy

This toolkit is built to comply with Drupal.org's policy on the use of AI when contributing to Drupal, not to work around it. The policy's core principle is that you are fully responsible for the integrity of your submission, and "the AI wrote it" is never an acceptable answer. That's why every agent in this repo is built around hard approval gates instead of autonomous posting:

  • Nothing reaches Drupal.org without a human reading it first. Code/dependency changes, staging, commits, and pushes require scoped approval. Recon and issue-record writes are automatic exceptions. Public posts are drafted for the human. See drupal-issue-agent's approval gates above.
  • AI involvement is disclosed, every time. drupal-gitlab appends an AI-Generated: line to every MR body; drupalorg-comment-format does the same for issue comments (Markdown italic form for migrated/GitLab queues). This isn't optional formatting. It's required before anything is shown to the user for approval.
  • No submission goes out untested. The pre-push preflight in A10/B5 blocks staging until PHPCS, PHPStan, and relevant tests pass locally, on top of whatever CI already enforces.
  • Prior discussion is read, not steamrolled. The A6 timeline cross-reference and cross-issue ## Related Issues memory exist specifically so the agent doesn't repeat a proposal a maintainer already rejected, or miss a reviewer thread nobody replied to.
  • Posting is a commitment, not a drop-and-run. A11's comment draft reminds the user that posting means being ready to follow up when a maintainer or reviewer responds. The policy treats drive-by AI patches with no follow-up as a bannable pattern.
  • Licensing and provenance are checked, not assumed. All contributed code must stay GPL-2.0-or-later compatible, and the A7 review checklist flags code that reads as copied verbatim from a non-GPL source rather than written for the context at hand.
  • Security issues never touch the public queue. If a review surfaces a vulnerability, the agent stops and directs the human to report it privately to the Drupal Security Team instead.

The contribution responsibilities are expressed in prompts. Client permissions and trusted hooks additionally restrict supported commands, but are not a complete security boundary. The workflow still depends on the human in the loop actually reads each [PAUSE] report and approves deliberately rather than reflexively. If you're extending this toolkit, keep new automation behind the same gates. See Developing this repo for the conventions that keep it that way.

Review philosophy: move issues toward RTBC

Every review this package produces, the light preliminary one in drupal-issue-start Phase 2.5 and the full one in drupal-issue-agent's A9, ends with a judgment call:

  • RTBC-ready
  • Close with a named gap
  • Needs work with a named gap
  • Needs discussion

The goal is a mergeable, community-acceptable contribution, not an exhaustively long findings list. Cosmetic nitpicks that don't block correctness, security, or standards get mentioned once and set aside.

Git guardrail hook

Both client adapters register a PreToolUse hook (templates/hooks/block-dangerous-git.sh) that hard-blocks destructive git commands regardless of the permissions allow list:

  • git reset --hard
  • git clean -f / -fd
  • git branch -D
  • git checkout . / git restore .

These discard local work with no recovery path. Adapted from mattpocock/skills' git-guardrails-claude-code.

Normal git push and --force-with-lease remain available; bare --force is blocked. drupal-issue-reroll force-pushes rerolled branches to the user's own issue fork as a normal, expected step, guarded by --force-with-lease and scoped approval. See client-specific permission limits above.

The same script also blocks reading secret material via common dump commands (cat, grep, head, cp, curl, and similar), and writing to it — via writer commands (tee, dd, install) and via shell output redirection (>/>>) — so Codex can't be routed around the deny list below by shelling out instead of using its native edit tool. Both directions match the same paths: .env/.env.* (excluding non-secret suffixes like .example/.sample/.dist/.template/.defaults/.test), *.pem/*.key/*.pfx/*.p12, SSH private keys, .netrc/.npmrc, and anything under a secrets/, .ssh/, or .aws/ path. It reuses the hook's shell--c-unwrapping, so bash -c "cat .env" is caught the same as a bare cat .env. templates/settings.json.template's permission deny list adds the Claude-Code-only complement — Read/Edit denials on the same paths, which blocks Claude's native file tools even with no Bash call involved. There's deliberately no Write(...) rule for these paths: Claude Code's permission matcher only honors Edit(path) rules for file-write checks, so a Write(...) rule is dead weight the harness itself flags as unenforced — Edit(...) alone already covers every file-editing tool. Codex has no equivalent per-tool permission concept, so for Codex this hook is the only protection. Both layers are best-effort string/glob matching, not a sandbox.

MCP servers

ServerBinaryPurpose
drupalorg-cli{{DRUPAL_CLI_BIN}} (detected via which drupalorg)Drupal.org issue/MR data

As of drupalorg-cli 0.12.0 this server exposes 17 read-only tools. gitlab_issue_show works correctly for migrated GitLab issues (but doesn't return comments); issue_show gained a withComments param in 0.12.0, but only for non-migrated issues. Tools that resolve a project from a classic nid alone (mr_list, mr_status, mr_files, issue_get_fork) are still broken for migrated issues at the MCP layer — the underlying CLI commands were fixed in 0.11.0 to accept a <project>#<nid> form, but the MCP tool schemas were never updated to expose that, so the fix isn't reachable through this MCP server. drupal-issue-start's glab mr list --search Bash fallback is still the working path for MR discovery there.

A native GitLab MCP for git.drupalcode.org is tracked at drupal.org/project/infrastructure/issues/3557469. It's blocked on GitLab Duo, a paid feature not yet available on Drupal's infrastructure.

Developing this repo

No build step or npm dependencies. CI runs Node built-in tests (Python 3.11+ validates TOML), frontmatter checks, and template checks:

# Syntax-check the setup script
node --check bin/setup.js
node --test tests/*.test.js

# {{VAR}} placeholders may only appear in templates/, from the known set
# (DDEV_PROJECT, SITE_URL, PHP_VERSION, MARIADB_VERSION, DRUPAL_PATH,
#  DRUPAL_WEBROOT, DRUPAL_CLI_BIN, SITES_TABLE)
grep -rn "{{" skills/ agents/   # must be empty

# templates/settings.json.template must be valid JSON once vars are substituted
node -e "JSON.parse(require('fs').readFileSync('templates/settings.json.template','utf8').replace(/\{\{[A-Z_]+\}\}/g,'placeholder'))"

To test bin/setup.js end-to-end against a real workspace:

cd /path/to/drupal-workspace
npx /path/to/this/repo

Then verify: no {{VAR}} left in installed skills/agents, the lockfile was written, and MCP servers appear in .mcp.json (Claude Code) or .codex/config.toml (Codex). Re-running is non-interactive once the lockfile exists.
